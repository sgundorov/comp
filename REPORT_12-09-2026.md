## 1. Назначение проекта

**«Компаньон»** — самописная CRM/ERP-система для малого и среднего бизнеса: учёт контрагентов, номенклатуры, склада, документов, денег, инвентаризации и аренды.

| Параметр | Значение |
|---|---|
| Назначение | Учёт и управление бизнес-данными через браузер |
| Платформа | PHP 8.2 + MySQL (mysqli) + vanilla JavaScript |
| Язык интерфейса | Русский |
| База данных | `comp` (по `config.local.php`), 67 таблиц |
| Фреймворки | **отсутствуют** — собственный «мини-фреймворк» |
| Внешние зависимости | **нет** (нет `composer.json`, `package.json`) |
| Лицензия | присутствует (`LICENSE`) |

### Функциональные подсистемы (по меню и модулям)

| **Документы** | Счета, коммерческие предложения, кассовая книга (платежи), инвентаризация, аренда |

### Ключевая архитектурная идея

Каждая сущность реализована набором файлов по единому шаблону:

```
config/{entity}_columns.php       — описание колонок (метки, ширины, видимость)
config/{entity}_page.php          — конфиг TablePage (SQL, поиск, фильтры)
{entity}.php                      — страница-список
{entity}_form.php                 — модальная форма (new/edit/copy/delete)
{entity}_field_save.php           — AJAX инлайн-сохранение поля
{entity}_export.php               — экспорт CSV/XLS
{entity}_print.php                — печатная форма
{entity}_columns_save.php         — сохранение видимости/порядка колонок
{entity}_column_width_save.php    — сохранение ширины колонок
```

Два «столпа» системы: **`lib/TablePage.php`** (страница-таблица: поиск, сортировка, фильтры, пагинация, отметки, экспорт) и **`assets/form-modal-core.js`** (модальные формы: открытие, submit, stash/restore, autoInit).

```
index.php ──▶ {entity}.php ──────────────▶ lib/TablePage.php
                  │  ajax=1 → JSON              │
                  ▼                              ▼
          openFormModal() ──▶ {entity}_form.php ──▶ lib/controls.php
                  │                                  lib/table-template.php
                  ▼
          {entity}_field_save.php  (инлайн-правка → JSON)
```

## 3. Достоинства

### 3.1 Архитектурные

1. **Единый стандарт UI/UX.** `DESCRIPTION.md` задаёт жёсткий стандарт, и он реально соблюдается: все таблицы и формы выглядят и работают одинаково. Это редкое качество для самописных систем.
2. **Богатый функционал «из коробки»** на каждой странице-таблице: быстрый поиск + многоколоночные условия, многоуровневая сортировка, колоночные фильтры, пагинация, инлайн-редактирование, lookup-выбор из справочников, изменение ширины/порядка/видимости колонок с сохранением в БД, отметки записей, переживающие навигацию, экспорт CSV/XLS, печать (все/выбранные/текущая страница), горячие клавиши, адаптивная вёрстка.
3. **Нулевые зависимости.** Работает на любом LAMP-хостинге; развёртывание = копирование файлов. Нет проблем с версиями пакетов и supply-chain.
4. **Единый механизм модальных форм** (`FormModalCore`) со stash/restore — позволяет открывать дочерние формы поверх родительских без потери состояния.
5. **Шаблонизатор печатных форм** с разметкой `#Var#`, `#D1…#1D` — и конвертация унаследованных RTF-шаблонов в HTML.
6. **Серверная защита критичных операций**: блокировка редактирования утверждённых документов (`accept_flag`), запрет удаления последнего администратора, серверные guard'ы для inline-правок и дочерних таблиц (клиентскую блокировку можно обойти — серверную нет).

### 3.2 Инженерные

7. **Отличная документация.** Комбинация «спецификация + архитектура + конвенции + журнал сессий + руководство пользователя» — редкость даже для коммерческих проектов.
8. **Работающие тесты.** PHPUnit без Composer: 68 unit-тестов зелёные, 34 интеграционных проходят, есть фикстуры и авто-запуск сервера. Ключевые бизнес-расчёты (аренда) покрыты отдельно.
9. **Осмысленная работа со сложной бизнес-логикой**: тарифы аренды (часовые/дневные/месячные/фиксированные, сезоны, выходные, НДС, залог), пропорциональный пересчёт при досрочном возврате, пересчёт итогов документа из позиций, бронирование с проверкой пересечения периодов.
10. **Права доступа по ролям и объектам** (`dostup`, `role`, `object`) с блокировкой пунктов меню и полей.
11. **Консистентность после рефакторингов** — в журнале видно систематическую работу по унификации (перевод страниц на `store.php`-паттерн, вынос `EmbeddedTable`, единый рендер колонок).

## 4. Недостатки и риски

### 4.1 Критичные

1. **Нет серверной аутентификации.**
   Проверено экспериментально: `GET /city.php` **без сессии возвращает HTTP 200 и 20 строк реальных данных** — вход реализован как клиентский overlay (`lib/table-template.php:28-58`). Любой может получить данные напрямую по URL или дёрнуть AJAX-endpoint. Это главный риск проекта.

2. **Пароли хранятся в открытом виде.**
   `login_handler.php:28`: `if (!$r || $r['passw'] !== $password)` — прямое сравнение строк, без `password_hash()`/`password_verify()`. Утечка БД = компрометация всех учётных записей.

3. **Отсутствие CSRF-защиты.** Все POST-endpoint'ы (`*_field_save.php`, `*_form.php`) принимают запросы без токена.

### 4.2 Архитектурные

4. **Массовое дублирование кода.** 9 файлов на сущность × 32 сущности. Копипаста при создании новой таблицы приводит к «десяткам ошибок» — это прямо зафиксировано в `111.txt` («мы опять получили ДЕСЯТКИ ошибок и недоделок, исправление которых заняло много часов отладки»). Скилл-шаблон проблему не решил.

5. **Гигантские файлы, низкая читаемость.**

   | Файл | Строк |
   |---|---|
   | `lib/TablePage.php` | 2 588 (166 функций) |
   | `sale.php` | 1 226 |
   | `arenda2_form.php` | 1 195 |
   | `tmc_form.php` | 1 182 |
   | `invoice.php` | 1 140 |

   Один класс на 2,5 тысячи строк с 166 методами — высокая цена любой правки.

6. **Смешение PHP + HTML + JS в одном файле**, JS в строковых литералах и `eval` при загрузке модалок. Отладка требует браузера, статический анализ невозможен.

7. **Нет миграций БД.** Схема меняется ad-hoc: `ensure_*_table()` и `ALTER TABLE` выполняются при каждом запросе из `config.php` (строки 34-36, 86-102). Окружения легко расходятся; изменения схемы невидимы в истории.

8. **«Каждая страница — entry point».** Нет фронт-контроллера и API; AJAX определяется по `$_GET['ajax']`. Любая интеграция или мобильный клиент потребуют переписывания.

9. **`mysqli_report(MYSQLI_REPORT_OFF)`** — ошибки БД глушатся, сбои проявляются как пустые выборки.

10. **Неявная зависимость от глобальных флагов** `app_settings` (`ManualTariffFlag`, `KeepDaysOnEarlyReturn`, `ShowMonthsFlag`…): поведение модуля меняется без изменения кода, что усложняет тестирование и воспроизведение багов.

### 4.3 Инфраструктурные

11. **Мусор в репозитории ~164 МБ:**

    | Каталог/файл | Размер | Комментарий |
    |---|---|---|
    | `.opencode--/` | 107 МБ | `node_modules` от стороннего инструмента |
    | `.mimocode.bak/` | 57 МБ | резервная копия инструмента |

    Плюс битые копии: `firm_form — копия.php` (**parse error**, строка 95), `client--.php`, `city_form-.php`, `opencode-.json`, `opencode=.json`, `out.txt`, `fix_encoding.ps1`.

12. **Незакоммиченные изменения** — включая активную работу по «Аренде»: нет чистого состояния, риск потери.

13. **CI/CD отсутствует**, тесты не запускаются автоматически; 106 из 140 интеграционных тестов скипаются по умолчанию (не поднимается сервер).

14. **Не реализовано из исходного ТЗ**: импорт записей из CSV (`import.php` отсутствует), раздел «Услуги» (`service.php` отсутствует), «Коммерческие предложения» как отдельная сущность.

15. **Мелочи**: 7 мест с интерполяцией переменных в SQL-строку (в основном тесты + `arenda_form.php:141`); `deprecation`-предупреждения PHPUnit (101 шт.).

### 4.4 Известные «хвосты» функционала (по журналу)

- Аренда: месячный тариф из `price` (колонки `bmonths/emonths/mprice`) не выбирается — берётся из `product.price_month`.
- Аренда: `docum2.discount` копируется из документа, а не из поля формы товара (при этом `sum` считается по введённой скидке).

## 5. Возможности развития

### Приоритет 1 — безопасность (обязательно)

| Задача | Суть |
|---|---|
| Серверный guard аутентификации | Проверка `$_SESSION['sotr_id']` в начале `config.php`: неавторизованный запрос → 302 на страницу входа / 401 для AJAX. Убрать выдачу данных до логина |
| Хеширование паролей | `password_hash()` / `password_verify()` + миграция существующих записей |
| CSRF-токены | Скрытое поле/заголовок во всех формах и AJAX-запросах |
| Усиление сессии | `session_regenerate_id()` после входа, `HttpOnly`/`SameSite` cookies |

### Приоритет 2 — снятие «налога на копипасту»

1. **Метаданные сущностей.** Описать таблицу/форму декларативно (один PHP-массив или JSON: поля, типы, лукапы, права) и генерировать из них `columns`, `page`, `field_save`, `export`, `print`. Это прямо адресует проблему из `111.txt` — «десятки ошибок» при создании новой таблицы.
2. **Декомпозиция `lib/TablePage.php`** на независимые классы: `QueryBuilder`, `FilterBuilder`, `TableRenderer`, `Pagination`, `ExportService`.
3. **Вынос JS из PHP-строк** в `assets/` + отказ от `eval` при инициализации модалок.
4. **Миграции БД.** Ввести простой runner (или Phinx) и перенести все `ALTER`/`ensure_*` из `config.php` в версионированные миграции.

### Приоритет 3 — инфраструктура и гигиена

5. **CI (GitHub Actions):** `php -l` по всем файлам + `phpunit --testsuite unit` на каждый push; интеграционные тесты — отдельной job с автоподъёмом сервера.
6. **Чистка репозитория:** удалить `.opencode--/`, `.mimocode.bak/`, битые копии (`firm_form — копия.php`, `client--.php`, `city_form-.php`), `out.txt`, `opencode*.json`; добавить в `.gitignore`.
7. **Закоммитить незавершённую «Аренду»** или вынести в отдельную ветку.

### Приоритет 4 — продукт

8. **JSON/REST API** поверх существующих endpoint'ов → мобильный клиент, интеграции, внешние отчёты.
9. **Завершить «Аренду»**: тариф за месяц из `price`, корректный `discount` товара, автоматизация доплат при просрочке.
10. **Реализовать заявленное в ТЗ**: импорт CSV, раздел «Услуги», отдельная сущность «Коммерческие предложения».
11. **Журнал аудита**: таблица `history` уже есть — расширить до полного лога изменений (кто, что, когда) с UI-просмотром.
12. **Производительность**: клиенты 20k+, контакты 27k+ — проверить индексы и `EXPLAIN` тяжёлых списков, рассмотреть серверную пагинацию/кэш.
13. **Справка в приложении**: готовое руководство `docs/` (15 страниц) вывести в меню («Справка») вместо отдельного каталога.

## 6. Итоговая оценка

**«Компаньон» — зрелая, работающая бизнес-система**, покрывающая полный цикл торгово-складского учёта: 67 таблиц БД, 32 сущности с единым интерфейсом, ~56 тыс. строк PHP и ~4,5 тыс. строк JS, реальные рабочие данные (20 тыс. контрагентов, 27 тыс. контактов), зелёные тесты и документация уровня коммерческого продукта.

**Сильные стороны:** консистентный UX, богатый функционал каждой таблицы, нулевые зависимости, отличная документация, продуманная сложная бизнес-логика (аренда, инвентаризация).

**Главные ограничения:** отсутствие серверной аутентификации и хеширования паролей (критично), дублирование кода по 9 файлов на сущность, «монолитные» файлы на 1–2,5 тыс. строк, отсутствие миграций БД и CI, ~164 МБ мусора в репозитории, незакоммиченная работа по «Аренде».

**Рекомендуемый первый шаг:** закрыть контур безопасности (серверный guard + хеши паролей + CSRF) — это единственная группа проблем, которая при эксплуатации в сети создаёт необратимые последствия. Далее — метаданные/генератор сущностей как основной способ остановить накопление ошибок при росте системы.
